# Roadmap развития Music Orchestrator

Приоритизированный план апгрейдов поверх текущей MVP-базы (Go backend + React web + Flutter mobile). Оценка сложности: 🟢 малая (1–3 дня), 🟡 средняя (1–2 недели), 🔴 большая (несколько недель, требует архитектурных решений).

## Приоритет 1 — фундамент для остального

Всё ниже так или иначе на это опирается, поэтому делать в первую очередь.

### 1.1 Пагинация на `/v1/favorites`, `/v1/playlists`, `/v1/downloads` 🟢
Сейчас эти три эндпоинта отдают весь список целиком (в отличие от `/v1/search`, у которого уже есть `limit`/`offset`). У личной библиотеки, которая растёт годами, это рано или поздно станет медленным ответом и тяжёлым JSON на мобильном интернете.
**Зависимости:** нет. **Разблокирует:** комфортную работу с большой библиотекой на мобильном.

### 1.2 Уйти от одного JSON-файла с глобальным мьютексом 🔴
`store.go` — вся база (пользователи, избранное, плейлисты, задачи) в одном файле, один `sync.Mutex` на все операции. Для одного пользователя незаметно, но: (а) не переживёт несколько активных клиентов одновременно (веб + мобильный + второй пользователь), (б) каждая запись — перезапись всего файла целиком.
Рекомендация: SQLite (`modernc.org/sqlite`, без cgo) как встроенная замена — не требует отдельного сервиса, но даёт настоящие транзакции и запросы вместо полной сериализации. Миграция данных из существующего `store.json` — отдельный одноразовый скрипт.
**Зависимости:** нет, но чем позже — тем больнее переносить данные существующих пользователей. **Разблокирует:** пункты 3.2, 3.3.

## Приоритет 2 — то, что просили явно

### 2.1 Добавление трека по ссылке (вставил URL — получил трек) 🟡
Сейчас единственный путь в библиотеку — поиск. Нужно: поле «Вставить ссылку» (YouTube/SoundCloud) на экране поиска, backend-эндпоint `POST /v1/resolve` принимает URL, достаёт video/track ID через уже существующий `extractor.go` (yt-dlp уже используется для стриминга — это переиспользование, не новая зависимость), возвращает `Track` в том же формате, что и `/v1/search`.
Важно сохранить текущую модель безопасности: работает только при `APP_ENABLE_RISKY_EXTRACTORS=true`, с тем же UI-предупреждением о временных потоках, что сейчас в баннере риска.
**Зависимости:** 1.1 не требуется. **Сложность в основном на фронте** (валидация URL, стейты ошибок «не удалось распознать ссылку»).

### 2.2 Рекомендации — «бесконечное радио» от трека 🟡
Полноценная ML-персонализация («Моя волна») требует данных о поведении тысяч пользователей — для self-hosted библиотеки одного-двух человек это нереалистично и не нужно. Реалистичная и полезная версия:
- **YouTube Mix/Radio**: `yt-dlp` умеет разворачивать YouTube-плейлист «RD…» (тот самый Mix, который YouTube сам строит по видео) — кнопка «Радио от этого трека» на экране Now Playing тянет 20–25 треков из готового Mix-а вместо того, чтобы изобретать рекомендательный алгоритм с нуля.
- **Автодобавление в очередь по автору**: когда очередь подходит к концу, backend подмешивает несколько треков того же исполнителя из уже проигранных источников (простое правило, не ML).
Обе фичи используют то, что уже есть в проекте (yt-dlp, providers), а не новую инфраструктуру.
**Зависимости:** 1.2 полезен (история прослушиваний для авто-очереди), но не обязателен для MVP-версии.

### 2.3 Другие фичи, которые реально поднимают ощущение «взрослого стриминга» (см. также исследование трендов в этом чате)
Отсортировано по соотношению «эффект / сложность»:

| Фича | Сложность | Почему стоит |
| --- | --- | --- |
| **Умные плейлисты** (авто-подборка «все скачанные», «топ за месяц» по счётчику прослушиваний) | 🟢 | Не требует новых данных — только счётчик play count, которого сейчас нет вообще |
| **Sleep timer / таймер сна** | 🟢 | Чисто клиентская фича (таймер + pause), никаких изменений в backend |
| **Кроссфейд между треками** | 🟡 | `just_audio` (Flutter) и Web Audio API (веб) оба это умеют «из коробки»; ощутимо поднимает субъективное качество плеера |
| **Текст песни (lyrics)**, если доступен через провайдера | 🟡 | Нужен новый провайдер-адаптер под lyrics API; не у всех треков будет доступен |
| **Статистика прослушивания** («сколько часов за неделю», топ-артисты) | 🟡 | Нужен новый счётчик событий на backend (сейчас его нет вообще — только факт лайка/скачивания) |
| **Second-user / семейный доступ с раздельными библиотеками** | 🔴 | Уже есть роли admin/user в auth.go — но избранное/плейлисты сейчас общие на весь стор, не per-user изолированные. Нужно менять схему данных |
| **Waveform-визуализация трека** (как в SoundCloud) | 🔴 | Требует анализа аудио на backend (генерация peaks) — заметный кусок работы ради чисто визуального эффекта, приоритет ниже остального |

## Приоритет 3 — качество и масштабирование

### 3.1 Реальные роуты в React (react-router-dom уже установлен, но не используется) 🟢
Сейчас переключение экранов — это `useState` внутри `SearchPage`, а не настоящие URL. Из-за этого нельзя дать ссылку на конкретный экран и не работает кнопка «назад» в браузере. Пакет уже в `package.json` — просто не подключён.

### 3.2 История прослушиваний как отдельная сущность 🟡
Нужна и для статистики (2.3), и для авто-очереди (2.2), и для «Слушай снова» на вебе и мобильном (сейчас это фактически «избранное», а не история). Требует 1.2 (SQLite) — вести историю событий в едином JSON-файле нецелесообразно.

### 3.3 Полнотекстовый поиск по локальной библиотеке 🟡
Сейчас поиск по локальным seed-трекам — подстрочное сравнение. Для библиотеки с сотнями скачанных треков стоит перейти на FTS5-индекс SQLite (бесплатно после 1.2) — поиск по опечаткам и частичным словам.

## Что сознательно не в приоритете

- **AR/VR-фичи** — на трендовых страницах упоминаются, но для self-hosted аудио-плеера не имеют практического смысла.
- **Полноценная ML-рекомендательная система** — см. 2.2, для этого масштаба продукта избыточна и не даст результата лучше, чем YouTube Mix.
- **Android-сборка Flutter-приложения** — сейчас в проекте настроен только iOS/macOS/web таргет (нет Android SDK в этом окружении); сама кодовая база кроссплатформенная, добавить Android — вопрос установки SDK и `flutter build apk`, отдельных архитектурных решений не требует.
