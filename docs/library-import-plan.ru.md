# Медиатека и импорт: системный анализ и план

Документ по итогам исследования перед реализацией. Здесь измерения, разбор готовых решений и порядок работ — чтобы не строить велосипед и не упереться в стену на середине.

---

## 1. Что мешает прямо сейчас

Хранилище — один JSON-файл, который **целиком сериализуется и переписывается при каждой записи** (`saveLocked` в `store.go`, вызывается из 17 мест). Всё держится в памяти под одним мьютексом, пагинации в выдаче нет.

Замер на текущем коде:

| Треков | Время импорта | На один трек |
|---|---|---|
| 200 | 138 мс | 0.7 мс |
| 1000 | 2.4 с | 2.4 мс |
| 3000 | **19.3 с** | 6.4 мс |

Стоимость одного трека растёт линейно, значит суммарное время **квадратично**. Экстраполяция: 5 000 треков ≈ 53 секунды, 10 000 ≈ 3.5 минуты — и это только метаданные, без копирования файлов и конвертации. Дальше каждый лайк снова переписывает весь файл.

**Вывод: импорт тысяч треков невозможен без замены хранилища.** Это не «желательно потом», а предусловие задачи.

---

## 2. На что опираемся

Искали проект с тем же стеком и той же задачей. Нашли эталон.

**[Navidrome](https://github.com/navidrome/navidrome)** — 21.6k звёзд, self-hosted музыкальный сервер:

| Их решение | Почему подходит нам |
|---|---|
| Go + встроенный SQLite | Наш язык; остаётся один бинарь без внешней БД |
| FTS5 для полнотекстового поиска | Ровно проблема «легко запутаться среди тысяч треков» |
| Многофазный конвейер сканера | Импорт как поток, а не как одна транзакция |
| `PRAGMA optimize` и `ANALYZE` после сканирования | Держит скорость запросов на больших библиотеках |
| Squirrel + репозитории | Типизированные запросы без тяжёлой ORM |

Берём: SQLite + FTS5, конвейерный сканер, репозитории. Не берём: Subsonic API и плагины на WebAssembly — нам не нужны.

Дополнительно смотрим на **Plex/Jellyfin** в части UX: библиотека там строится не плоским списком, а по осям «Исполнители → Альбомы → Треки» плюс фасетные фильтры (источник, жанр, год, наличие офлайн). Именно фасеты решают проблему «тысячи треков из разных источников».

## 3. Про iTunes и формат m4p — важное

Требование «автоконвертация m4p → mp3» выполнить нельзя, и причина не в трудоёмкости.

**`.m4p` — это файлы с DRM FairPlay.** Проверено: у ffmpeg в системе **ноль** упоминаний FairPlay и никаких средств для работы с такой защитой. Конвертация m4p требует снятия DRM, а это обход технических средств защиты — я такое реализовывать не буду.

Хорошая новость: **проблема почти наверняка не ваша**. Apple убрала DRM из музыкальных покупок ещё в 2009 году, и всё, что куплено после, — это `.m4a` **без защиты**. Библиотеки iTunes сегодня состоят из m4a, и они конвертируются свободно.

Что делаем:

- **Поддерживаем**: `m4a`, `mp3`, `flac`, `wav`, `aac`, `ogg`, `opus`, `wma` — то, из чего реально состоят библиотеки.
- **Читаем `iTunes Library.xml`** — оттуда берём плейлисты, рейтинги, счётчики прослушиваний и даты добавления. Это и есть «слушать медиатеку iTunes».
- **При встрече `.m4p`** импорт не падает: файл помечается как защищённый, и пользователь видит объяснение — такие треки нужно заново скачать из Apple Music в незащищённом виде, это штатная и бесплатная операция.

Так вы получаете рабочий импорт своей библиотеки, а проект не превращается в инструмент обхода защиты, который к тому же снесут с GitHub.

## 4. Порядок работ

Каждая задача проходит полный цикл: анализ → реализация → работоспособность → тесты БД → безопасность → нагрузка → внешний вид. Провал на этапе означает возврат, а не переход дальше.

### Задача 1. Хранилище на SQLite

Предусловие для всего остального.

- Схема: `tracks`, `artists`, `albums`, `playlists`, `playlist_tracks`, `favorites`, `jobs`, `sources`.
- FTS5-индекс по названию, исполнителю и альбому.
- Репозитории с параметризованными запросами — никакой конкатенации SQL.
- Миграция существующего `store.json` при первом запуске, старый файл сохраняется рядом как резервная копия.
- Пагинация во всех списках вместо выдачи всего разом.

Критерий успеха: импорт 10 000 треков **линеен** и укладывается в секунды, а не в минуты.

### Задача 2. Импорт файлов

- **Загрузка по сети**: `POST /v1/import` с потоковой многофайловой загрузкой, докачкой и прогрессом. Файлы пишутся на диск потоком, не в память.
- **Импорт из папки на сервере**: указать путь, сканер обходит дерево — так заливаются десятки гигабайт без загрузки через браузер.
- **Разбор тегов**: исполнитель, альбом, номер трека, год, обложка.
- **Дедупликация** по хешу содержимого, чтобы повторный импорт не плодил копии.
- **Конвертация** через ffmpeg в фоновой очереди, с ограничением параллелизма.
- **iTunes Library.xml**: плейлисты и метаданные.

Безопасность: обязательная проверка путей от обхода каталога (`../`), белый список расширений, лимит размера, проверка реального типа файла по содержимому, а не по имени.

### Задача 3. Интерфейс медиатеки

- Оси «Исполнители / Альбомы / Треки» вместо плоского списка.
- Фасетные фильтры: источник, наличие на устройстве, жанр, год.
- Мгновенный поиск на FTS5.
- Виртуализированные списки — без неё десять тысяч строк положат интерфейс.
- Дизайн не переделывается: используются существующие токены, акцент и компоненты.

## 5. Чем проверяем

| Этап | Как |
|---|---|
| Работоспособность | Полный цикл: импорт → появление в медиатеке → воспроизведение |
| База | Тесты репозиториев, миграции, целостность после сбоя |
| Безопасность | Обход каталога, SQL-инъекции, подделка типа файла, лимиты |
| Нагрузка | Импорт 10 000 треков, замер времени и памяти |
| Внешний вид | Playwright: медиатека, фильтры, прогресс импорта |
